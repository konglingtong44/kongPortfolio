# 工作单元拆分计划

依据：[需求](../requirements-analysis/requirements.md)、[已确认的拆分答案](units-generation-questions.md)。Domain Design 已因本次不新增应用组件而跳过；这里把文档与仓库整理视为交付成果，不把 S3、Lambda 等现有基础设施伪装成新组件。

## 边界与单元

| ID | 目录名 | 类别 | 交付成果 | 边界与验收重点 |
|---|---|---|---|---|
| U1 | `u1-learning-entry` | `spec` | 中文零基础入口与阅读顺序 | 从 `docs/learning/` 可进入项目、技术、AI、AWS、文件和规则主题；首次术语有解释，保留现有有效入口。 |
| U2 | `u2-file-map` | `spec` | 目录与项目手写文件地图 | 每个项目目录及版本管理中的手写文件有用途、所属功能和修改时机；生成和下载内容按类别说明，并链接至入口。 |
| U3 | `u3-technology-guide` | `spec` | 技术、AI、AWS 与替代方案指南 | 将源码可证实的实现与线上未核实状态分开；说明用途、好处、差异、取舍和选择理由，教学比较单独标识，并链接至入口。 |
| U4 | `u4-maintenance-guide` | `spec` | 规则和流程维护入口 | 指明项目约定、AI-DLC 方法、项目自定义技能与流程的修改位置和检查方法，并链接至入口。 |
| U5 | `u5-cleanup-proposal` | `spec` | 文件级清理候选方案 | 对每一候选列路径、用途、引用、历史价值、影响、验证和回退；无证据的项目不列为可删项；方案单独供项目负责人审核。 |
| U6 | `u6-approved-cleanup` | `packaging` | 获准的首个有界整理批次 | 仅执行 U5 中已经逐项获准的文件移动、合并、删除或配置整理；更新引用并记录前后检查。若候选过多，先执行一个可单独验证的批次，余下批次再拆成小单元。 |

这里的 `spec` 表示仓库中供人阅读和维护的文档成果；U6 的 `packaging` 表示仓库文件组织和支持配置的整理，不代表新增部署物或 AWS 发布。所有单元均在现有仓库内交付，网站/API 行为和 AWS 资源保持不变。

## 直接依赖

- U1 无依赖，独立形成可用的最小阅读入口。
- U2、U3、U4 各依赖 U1，因为它们要把新资料接入该入口；三者彼此没有代码或测试依赖。
- U5 依赖 U2、U3、U4，因为清理候选必须根据整理后的文件地图和导航判断重复与引用。
- U6 依赖 U5 的具体候选、审核结果和回退方案。没有获准的目标就不执行删改。

## 方案取舍

按成果拆分让每次审核对应一项读者或维护者可见的价值；按 `docs/`、脚本、配置等现有目录拆分会使一个单元同时包含多种目标，难以判断完成条件。目录和文件路径的精确修改清单留在各单元的实施计划，U5 的删改清单须先审阅。
