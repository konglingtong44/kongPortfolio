# 文档与目录整理工作单元

依据：[已批准的需求](../requirements-analysis/requirements.md)和[单元拆分计划](decomposition-plan.md)。本次没有新的应用组件；下列单元对应仓库中可单独审核的文档与整理成果。应用代码、API 和 AWS 资源边界保持不变。

| Unit ID | Directory | Kind | 成果及责任边界 | 交付形态 | 相对规模 |
|---|---|---|---|---|---|
| U1 | `u1-learning-entry` | `spec` | 建立中文零基础入口、阅读顺序和术语解释；保留已有有效导航 | 嵌入现有 `docs/learning/` | S |
| U2 | `u2-file-map` | `spec` | 按目录与手写文件记录用途、所属功能、修改时机；生成与下载内容按类别解释 | 嵌入现有文档结构 | L |
| U3 | `u3-technology-guide` | `spec` | 解释前后端、AI、AWS 与交付技术；写清好处、替代方案差异、取舍和真实证据状态 | 嵌入现有文档结构 | M |
| U4 | `u4-maintenance-guide` | `spec` | 指向项目规则、AI-DLC 方法、自定义技能和新增流程的位置及检查方法 | 嵌入现有文档结构 | S |
| U5 | `u5-cleanup-proposal` | `spec` | 对每项重复或过时候选写文件级证据、影响、验证、回退和审核状态 | 仓库内可审核方案，不执行删改 | M |
| U6 | `u6-approved-cleanup` | `packaging` | 仅执行 U5 获准的首个有界清理批次，更新引用并记录前后验证 | 现有仓库文件组织；不产生新部署物 | M（依候选规模复核） |

`spec` 单元交付可直接阅读的仓库资料；U6 的 `packaging` 指仓库文件和支持配置的有界整理，**不表示**创建新镜像、部署包或 AWS 资源。如果 U5 的获准候选超出一个小改动，U6 只涵盖首批，后续批次须拆出新的可审核单元。

## 单元验收边界

- U1：入口可导航到项目、技术、AI、AWS、文件和规则主题；新读者能据入口回答“项目做什么、前后端和 AWS 各做什么、AI 回答受什么限制、去哪里找文件用途与维护规则”。未讲清的术语或路径记入待修项。
- U2：版本管理中项目手写文件逐一可定位；每个有效目录有目的说明；无法核实的文件标待核实，不推断用途。
- U3：每项实际技术有代码或配置依据；教学比较标明非历史决策，AWS/Bedrock 未经线上查询的状态不写成已验证部署。
- U4：读者能从资料找到相应规则或流程的维护入口，知道哪些 AI-DLC 生成文件不应直接修改。
- U5：每项候选均有路径、用途、引用、历史价值、影响、验证和回退；没有证据的目标不列为可删；提交负责人单独审核。
- U6：仅对 U5 明确获准的目标实施；原有有效链接和网站/API 行为保持，相关本地检查有前后结果与未验证项。若无获准候选，本单元不执行删改。

## 共同约束

任何单元不得引入新框架或 AWS 资源、取消生产审批门、暴露密钥或改变访客可见行为。文档移动要更新相对链接，并运行 `node scripts/check-docs.mjs`；涉及脚本、依赖或配置的单元按实际影响运行相关前后端检查。历史记录保留其日期语境。
